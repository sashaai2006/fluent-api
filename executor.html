Постановка задачи

Есть направленный ациклический граф задач. Ребро a → b означает: «b нельзя запускать, пока не завершился a».

Нужен Executor, который:

  • исполняет задачи на пуле потоков,
  • соблюдает зависимости,
  • выжимает параллелизм из независимых ветвей,
  • корректно обрабатывает исключения.
      ┌───┐
      │ a │
      └─┬─┘
       ╱ ╲
      ▼   ▼
    ┌───┐┌───┐
    │ b ││ c │   b и c — параллельно
    └─┬─┘└─┬─┘
       ╲   ╱
        ▼ ▼
      ┌───┐
      │ d │              d ждёт ОБОИХ
      └───┘
«Ромб» — минимальный граф, проверяющий и параллелизм, и join-семантику.

Архитектура

Вся конкурентность сосредоточена в RunState и очереди. Граф читается без единой синхронизации.

TaskGraph после slimming'а

Из графа вынесен весь runtime: очередь готовых, статусы узлов, мьютекс, condvar, счётчики. Осталось строительство и валидация:

auto AddNode(InlineTask<void()> task) -> NodeId;
void AddEdge(NodeId from, NodeId to);
void Seal();   // проверка цикла + сборка CSR-ленты

// Read-only доступ для планировщика, только после Seal():
auto Task(NodeId id) const -> const InlineTask<void()>&;
auto Successors(NodeId id) const -> std::span<const NodeId>;
auto Indegrees() const -> std::span<const std::uint32_t>;
Важно: Seal() больше не удаляет indegree_ — это неизменяемый снапшот, из которого каждый RunState инициализирует свои счётчики.
Побочная правка: InlineTask::operator() стал const (как у std::function) — иначе задачи нельзя вызывать через shared_ptr<const TaskGraph>.

RunState — сердце прогона

struct Executor::RunState {
  std::shared_ptr<const TaskGraph> graph;
  std::unique_ptr<std::atomic<std::uint32_t>[]> unresolved; // счётчики предков
  std::atomic<std::uint32_t> remaining;   // узлов осталось учесть
  std::atomic<bool> failed{false};
  std::mutex error_mutex;
  std::exception_ptr first_error;         // пишется один раз
  std::promise<void> done;
};
  • Живёт в shared_ptr: каждый элемент очереди держит прогон живым.
  • unresolved[i] — сколько предков узла i ещё не завершились. Инициализируется из Indegrees().
  • remaining — сколько узлов ещё не учтено (не обязательно «не выполнено»!). Кто обнулил — тот выполняет promise.
  • Не копируется и не перемещается (atomic + mutex + promise) — и не нужно: всегда за shared_ptr.

BlockQueue — почему notify вне лока

template <typename U>
void Push(U&& t) {
  {
    std::lock_guard guard(mutex_);
    if (!open_) return;
    queue_.push(std::forward<U>(t));
  }
  cv_.notify_one();   // снаружи — ок!
}
std::optional<Task> Get() {
  std::unique_lock lock(mutex_);
  cv_.wait(lock, [&] {
    return !(open_ && queue_.empty());
  });
  if (queue_.empty())
    return std::nullopt;
  auto t = std::move(queue_.front());
  queue_.pop();
  return t;
}
Мьютекс защищает предикат (состояние очереди), а не сам notify. Missed wakeup невозможен: либо ждущий увидит непустую очередь при проверке предиката, либо получит notify. Notify вне лока — ещё и оптимизация: проснувшийся поток не упирается в занятый мьютекс.

Get() после Close() дочитывает остаток очереди → graceful drain бесплатно.

Submit: рождение прогона

auto Submit(std::shared_ptr<const TaskGraph> graph) -> std::future<void> {
  if (!graph || !graph->Sealed())
    throw std::logic_error{"...not sealed"};

  auto run = std::make_shared<RunState>(std::move(graph));
  auto future = run->done.get_future();

  if (run->graph->Size() == 0) { run->Settle(); return future; }

  {
    std::lock_guard lock(runs_mutex_);
    if (stopping_) throw std::logic_error{"...stopping"};
    ++active_runs_;                       // регистрация ДО посева
  }

  for (NodeId id = 0; id < graph->Size(); ++id)
    if (indeg[id] == 0)
      queue_.Push(WorkItem{run, id});     // сеем корни
  return future;
}
Порядок критичен: ++active_runs_ под тем же мьютексом, что и проверка в деструкторе — деструктор не может увидеть «ноль активных прогонов» посреди Submit.

Воркер: Loop и ExecuteNode

void Loop() {
  while (auto item = queue_.Get())   // nullopt ⇔ очередь закрыта и пуста
    ExecuteNode(*item);
}

void ExecuteNode(const WorkItem& item) {
  const auto& [run, id] = item;

  if (!run->failed.load(std::memory_order_acquire)) {
    try { run->graph->Task(id)(); }
    catch (...) { run->Fail(std::current_exception()); }
  }

  // обход потомков — ВСЕГДА, даже для пропущенного узла
  for (auto succ : run->graph->Successors(id))
    if (run->unresolved[succ].fetch_sub(1, std::memory_order_acq_rel) == 1)
      queue_.Push(WorkItem{run, succ});

  if (run->remaining.fetch_sub(1, std::memory_order_acq_rel) == 1) {
    run->Settle();          // promise — ровно один раз
    OnRunFinished();
  }
}

Сложное место №1: fail-fast без зависаний

  A ✗ (throw)
  │
  ▼
  B ← никогда не выполнится
  │
  ▼
  C ← и он тоже

Вопрос: кто доведёт
remaining до нуля?

Наивный вариант «не класть потомков упавшего в очередь» зависает: счётчик C никогда не обнулится, promise не выполнится, future.get() ждёт вечно.

Решение — единый учёт:

  • каждый узел ровно один раз попадает в очередь;
  • каждый узел ровно один раз уменьшает remaining;
  • пропущенный узел всё равно делает обход потомков.
После падения остаток графа «протекает» через очередь как no-op за O(V+E). Чужие прогоны в той же очереди не затрагиваются — отмена ленивая, по флагу run->failed.

Сложное место №2: promise выполняется один раз

void Settle() {
  if (first_error) done.set_exception(first_error);
  else              done.set_value();
}
  • set_value/set_exception дважды — std::future_error. Значит, нужна единственная точка.
  • Точка одна: remaining.fetch_sub(1) == 1 сработает ровно у одного потока за весь прогон — атомик гарантирует.
  • Этот же acq_rel-декремент даёт happens-before со всеми Fail() → first_error читается в Settle() без мьютекса.
Мьютекс вокруг first_error нужен только для гонки «два Fail одновременно» — первый выигрывает, второй exception_ptr просто уничтожается.

Сложное место №3: memory ordering

Требование: тело задачи-предка happens-before тела задачи-потомка.

  Поток 1 (предок a)              Поток 2 (последний предок)      Поток 3 (потомок b)
  ──────────────────              ──────────────────────────      ─────────────────────
  task_a()  ──sequenced-before──▶
  unresolved[b].fetch_sub(1,      unresolved[b].fetch_sub(1,      task_b() видит всё,
     acq_rel) // release             acq_rel) // == 1: acquire       что писали предки
                                        │
                                        ▼
                                  queue_.Push (под mutex) ──▶ Get() (под тем же mutex)
  • RMW-цепочка fetch_sub(acq_rel): каждый предок делает release, последний делает acquire и синхронизируется со всеми предыдущими декрементами.
  • Мьютекс очереди дотягивает happens-before до потомка.
  • Инициализация unresolved — relaxed: происходит в Submit до любой публикации.
Проверено инструментально: TSan молчит на всех 31 тесте.

Протокол остановки: graceful drain

~Executor() {
  {
    std::unique_lock lock(runs_mutex_);
    stopping_ = true;                          // новых Submit нет
    runs_cv_.wait(lock, [&] { return active_runs_ == 0; });
  }
  // все прогоны settled ⇒ очередь пуста, воркеры спят в Get()
  queue_.Close();                              // будим воркеров
}  // jthread'ы join'ятся автоматически
  • Инвариант «Push в закрытую очередь невозможен» держится на протоколе: Close() вызывается только когда active_runs_ == 0.
  • Порядок членов в классе важен: queue_ объявлена раньше workers_ → воркеры join'ятся до разрушения очереди.
  • Пусть promise прогона выполнен до возврата из деструктора — future у пользователя остаётся валидным.

Компромиссы и ограничения

  • Одна очередь = один мьютекс. При тысячах мелких задач — точка contention. Work stealing осознанно отложен: задачи не порождают подзадач.
  • Fail-fast через drain. Остаток упавшего графа протекает через очередь как no-op: O(V+E) на отмену, зато единый учёт узлов.
  • Нет приоритетов и отмены по запросу — только fail-fast по исключению.
  • Задачи — void() без возвращаемых значений. Результаты — через захваченные ссылки, как в тестах.
  • hardware_concurrency() == 0 сводится к одному потоку.

Что унести с собой

1. Иммутабельные данные не требуют синхронизации — выносите runtime из структур.

2. Единый учёт («каждый узел учтён ровно один раз») важнее хитрой отмены.

3. Promise выполняет тот, кто обнулил счётчик, — и никто больше.

4. Мьютекс защищает предикат, а не notify.

5. TSan — часть определения «готово».
